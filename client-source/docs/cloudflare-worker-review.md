# مراجعة Cloudflare Worker: `becare-public-gateway`

تمت مراجعة شيفرة الـWorker المنشور بتاريخ 4 أغسطس 2026. هذه المراجعة توثيقية ولا تتضمن أي قيمة سرية.

## السلوك الحالي

| المجال | السلوك |
|---|---|
| التحقق من المصدر | يتطلب ترويسة `Origin` ببروتوكول HTTPS، ويسمح بـ`https://sholomolo.com`، أو أي نطاق فرعي من `*.manus.space`، أو النطاقات المعرفة في `ALLOWED_ORIGINS`. |
| المسارات المسموحة | `GET /api/v1/sessions/current`، و`GET /api/v1/visitors/challenge`، و`POST /api/v1/visitors/register`، و`POST /api/v1/visitors/heartbeat`، و`POST /api/v1/sessions` فقط. |
| Turnstile | يتطلب تذكرة Turnstile لمسارات التسجيل والنبض وإنشاء الجلسة، عبر `X-Turnstile-Token` أو حقل JSON باسم `turnstile_token` أو `turnstileToken`. |
| عنوان العميل | يتطلب `CF-Connecting-IP` من بيئة Cloudflare، ويرفض الطلب عند غيابه. |
| التوقيع | ينشئ تذكرة HMAC قصيرة الصلاحية مدتها 20 ثانية ويرسلها إلى الخلفية ضمن ترويسات `X-DataFlow-Edge-*`. |
| التمرير للخلفية | يمرر الطلب إلى `BACKEND_URL` مع ترويسة التحقق `X-BCare-Origin-Token` المشتقة من `ORIGIN_GATEWAY_TOKEN`. |
| CORS | يعيد CORS للنطاق المقبول ويمنع تمرير `Set-Cookie` إلى المتصفح. |

## متغيرات Worker المطلوبة

| المتغير | الغرض |
|---|---|
| `BACKEND_URL` | عنوان الخلفية الموثوقة التي تستقبل المسارات المسموح بها. |
| `ORIGIN_GATEWAY_TOKEN` | تذكرة تحقق بين الـWorker والخلفية. |
| `EDGE_REQUEST_SIGNING_SECRET` | سر HMAC لتوقيع تذكرة الحافة. |
| `EDGE_TICKET_CURRENT_KEY_ID` | معرّف مفتاح آمن وقابل للدوران لتذكرة الحافة. |
| `TURNSTILE_SECRET_KEY` | سر تحقق Turnstile لمسارات POST المحمية. |
| `ALLOWED_ORIGINS` | قائمة اختيارية مفصولة بفواصل لنطاقات HTTPS الإضافية المسموح بها. |

## فجوة التوافق قبل الربط

واجهة BCare الحالية تستدعي `/api/laravel/api/v1/*` و`/api/vehicle-inquiry`، بينما الـWorker لا يقبل هذه المسارات ولا يمرر `Cookie` من الطلب الوارد. لذلك يجب توسيع قائمة المسارات في الـWorker و/أو تحديث الواجهة لتستخدم العقود المسموح بها، مع التأكد من أن الخلفية تدعم تذاكر `X-DataFlow-Edge-*` بدلاً من جلسات الكوكيز. لا يجب تبديل التطبيق إلى الـWorker قبل تنفيذ هذا التوافق واختباره.

## نتائج النشر والتحقق — 4 أغسطس 2026

تم تحديد العنوان العام للـWorker بأنه `https://becare-public-gateway.dariatameen.workers.dev`، والخلفية المعرفة في `BACKEND_URL` هي `https://sholomolo.com`. نُشر تحديث مقيد عبر Cloudflare API باستخدام `bindings_inherit=strict` وbindings من نوع `inherit` للأسرار؛ لم تُقرأ القيم السرية أو تُستبدل.

| الفحص | النتيجة | التفسير |
|---|---|---|
| `GET /api/laravel/api/v1/visitors/challenge` مع Origin Manus وهوية جوال | `200` | تحويل بادئة Laravel القديمة وتوقيع Worker يبلغان الخلفية بصورة صحيحة. |
| مسار API غير مسجل | `404 ROUTE_NOT_REGISTERED` | يظل السلوك default-deny فعالاً. |
| `GET /api/laravel/api/v1/sessions/contract-probe` | `404 Session not found` من الخلفية | المسار يعبر Worker ويصل للخلفية؛ المعرّف التجريبي غير موجود. |
| `GET /api/laravel/api/v1/sessions/current` من دون بيانات جلسة | `403 EDGE_TICKET_SIGNATURE_INVALID` | عقد المسار موجود لكن الخلفية تتطلب سياق/توقيع جلسة متوافقاً لا يمكن اختباره بلا جلسة حقيقية. |
| `POST /api/vehicle-inquiry` بجسم فارغ | `403` من الخلفية يذكر الموقع أو المفتاح | Worker يمرر المسار، لكن الخلفية تحتاج ضبطاً/اعتماداً إضافياً لهذا العقد قبل اختبار الاستعلام الحقيقي. |
| `POST /api/laravel/broadcasting/auth` من دون مصادقة | `401 Unauthenticated` | تمرير مسار Reverb يعمل والخلفية تطلب مصادقة صحيحة. |
| `POST /pusher/auth` | `404` من الخلفية | لا يوجد مسار Pusher في الخلفية الحالية، ولذلك أزيل من قائمة Worker المنشورة. |

تم أيضاً تعديل مرحلة بناء BCare بحيث تستبدل قاعدة API في الحزمة المبنية بعنوان الـWorker، وتعيد توجيه طلب المركبة إليه، مع الاحتفاظ بإصلاح HTTP 429. خادم Manus لم يعد يسجل بروكسي الأعمال؛ تستمر مسارات API المحلية غير المعرفة بإعادة `404` بدلاً من تقديم SPA أو تمريرها للخلفية.

### ملاحظة تحقق مرئي مفتوحة

أظهر فحص الهاتف في بيئة المعاينة بعد تحويل أصول الواجهة شاشة «مشكلة في الاتصال». لا تُعد التوسعة جاهزة للتسليم قبل تشخيص طلب bootstrap الفاشل من سجل الشبكة/وحدة التحكم وإصلاحه، ثم إعادة التحقق المرئي.

فتح المعاينة في المتصفح أعاد الشاشة نفسها، ولم تسجل وحدة التحكم أي رسالة صريحة؛ لذلك يكون التشخيص التالي من قائمة طلبات Resource Timing مع تجنب إجراء أي تسجيل أو إنشاء جلسة حقيقية.

أظهرت قائمة Resource Timing أن bootstrap يطلب `POST https://becare-public-gateway.dariatameen.workers.dev/api/v1/visitors/register`. أضيفت مراقبة مؤقتة لـ`fetch` في جلسة المتصفح لالتقاط رمز الاستجابة عند الضغط على «إعادة المحاولة»؛ لا تغيّر هذه المراقبة محتوى الطلب أو ترسله وحدها.

تم حقن مفتاح Turnstile العام المطابق للـWidget في الحزمة وتوسيع نطاقات الـWidget لتشمل `bcareapp-cqsxcdmi.manus.space` و`manus.computer` و`manus.space` و`sholomolo.com`. أظهر المتصفح العادي بعد ذلك الصفحة العامة بنجاح. بقيت لقطة viewport الهاتف من أداة المعاينة على شاشة الاتصال لأن الأداة تغيّر أبعاد العرض فقط بينما ترسل User-Agent لسطح المكتب؛ الخلفية ترفض هوية سطح المكتب عمداً. لذلك لا تعد هذه اللقطة دليلاً على فشل متصفح جوال حقيقي؛ يلزم اختبار جوال حقيقي أو بيئة تمكن تغيير User-Agent لإكمال تحقق التسجيل مع Turnstile دون إنشاء تسجيل فعلي.

حدّث Worker لاحقاً `User-Agent` الصادر إلى الخلفية إلى هوية جوال موثوقة، بما يطابق عقد البروكسي الأصلي مع الاحتفاظ بهوية العميل داخل تذكرة الحافة. بعد نشر التحديث، أعاد فتح المعاينة الصفحة العامة بنجاح ولم تعد شاشة الاتصال ظاهرة في التحقق المرئي على سطح المكتب.

أظهر فحص viewport الهاتف في أداة المعاينة شاشة الاتصال مرة أخرى، لكن الأداة لا تغيّر User-Agent الفعلي. أظهرت القراءة الآمنة مباشرة عبر Worker بهوية جوال ونطاق المعاينة `200` لمسار challenge؛ لذلك بقي الاختبار الحي للـTurnstile وتسجيل الزائر مؤجلاً لتجنب إنشاء بيانات مستخدم بلا تفويض صريح.

## نتائج العقود المتبقية

بعد توحيد User-Agent الصادر من Worker، صار `GET /api/laravel/api/v1/sessions/current` يعيد `404 Session not found` من الخلفية عند غياب جلسة بدلاً من `EDGE_TICKET_SIGNATURE_INVALID`، ما يثبت عبور العقد وتوقيعه. أعيدت كتابة `authEndpoint` الخاص بـReverb في أصل realtime ليطلب `https://becare-public-gateway.dariatameen.workers.dev/api/laravel/broadcasting/auth`، وأعيد Worker لتمرير `Set-Cookie` بعد إزالة `Domain` الخاص بالخلفية، مع CORS credentials.

يظل مسار المركبة غير محسوم: تمريره إلى `sholomolo.com` يعيد `403` برسالة أن الموقع أو المفتاح غير صحيح مع جسم فارغ. جُرّب توجيهه الصريح إلى `https://vehibook.com` كما يوثق المشروع الأصلي، لكنه أعاد `522` من خلال Worker، ولذلك أعيد فوراً إلى الخلفية المتاحة `sholomolo.com` لتجنب تعليق الطلبات. لا يلزم تعديل سر Worker حالياً؛ يلزم تحديد عقد/اعتماد الخلفية الصحيح لمسار المركبة قبل اعتبار تدفقه مكتملًا.

تحقّق المتصفح من تحميل مكتبة Turnstile الرسمية بنجاح وأن `window.turnstile` متاح. سيتحقق الاختبار التالي من تذكرة Turnstile ومسار تسجيل الزائر فقط باستخدام معرف/بصمة اصطناعيين، من دون بيانات هوية أو مركبة أو طلب عرض تأمين.

نفّذ اختبار التذكرة غير الشخصي في متصفح المعاينة، لكن Turnstile لم يعطِ callback خلال 18 ثانية (`TURNSTILE_TIMEOUT`) ولم يسجل المتصفح تشخيصاً إضافياً. لذلك لا يمكن إثبات مسار POST المحمي من بيئة الأتمتة نفسها؛ يلزم اختبار جوال حقيقي أو جلسة متصفح عادية من المستخدم. لم يُرسل الاختبار أي طلب تسجيل أو بيانات شخصية بعد انتهاء المهلة.

أضيف نطاق المعاينة الدقيق إلى إعدادات Widget وأعيد تحميل الصفحة، ثم تكررت مهلة Turnstile من بيئة الأتمتة. هذا يؤكد أن القيد هو تحقق Turnstile في المتصفح المؤتمت لا عدم تطابق النطاق؛ لم يُنشأ سجل زائر أو طلب عرض في أي من المحاولتين.

## تدقيق واجهة Worker

كان رابط QR في صفحة سطح المكتب يشير إلى `bcare-spa-gdkwxzkl.manus.space`، وهي نسخة سابقة يمكن أن تعيد المستخدم إلى تدفق البروكسي القديم. استُبدل في المصدر والإنتاج بالنطاق الحالي `bcareapp-cqsxcdmi.manus.space`. كما أصبح أساس API في الحزمة `https://becare-public-gateway.dariatameen.workers.dev/api/v1`، وأصبح endpoint المصادقة اللحظية عنوان Worker نفسه. أظهر Resource Timing في المعاينة الطلب الفعلي إلى Worker مباشرة، دون طلب API أعمال إلى نطاق Manus المحلي.

تحوّل أيضاً `wsHost` في حزمة Reverb من `location.hostname` إلى Host الخاص بالـWorker، وأضيف مسار `/ws` مقيد في Worker يقبل ترقيات WebSocket فقط ويرفض المسارات غير المعرفة. لم تتوفر نقطة Reverb صالحة في الخلفية للاختبار الكامل؛ اختبار `/ws` مع مفتاح staging المضمّن أعاد `404` من الخلفية، وهو إعداد خلفي مستقل عن إزالة بروكسي Manus.

أظهرت لقطة معاينة واحدة شاشة الاتصال، بينما أعاد فتح الصفحة بالمتصفح نفسه الصفحة العامة بنجاح. سيجري التشخيص من طلبات الشبكة قبل اعتماد نتيجة اللقطة، لأن أداة اللقطات تغير أبعاد العرض فقط وقد تختلف هويتها عن جلسة المتصفح العادية.

أكد فحص Resource Timing أن bootstrap يطلب `https://becare-public-gateway.dariatameen.workers.dev/api/v1/visitors/register`. وأعاد طلب متصفح مباشر غير منشئ للبيانات إلى العنوان نفسه `428 TURNSTILE_REQUIRED` مع `viaWorker: true`؛ أي أن المسار يصل إلى Worker كما ينبغي، وأن الرفض الحالي لطلب بلا تذكرة هو سياسة Turnstile وليس مروراً عبر بروكسي Manus.

بعد إعادة تشغيل المعاينة، ظهرت الصفحة العامة بصورة سليمة مع رابط QR الحالي، ولم يسجل المتصفح أخطاءً في وحدة التحكم. لذلك لم يعد دليل لقطة الشاشة المنفردة كافياً لاعتبار اتصال Worker مكسوراً.

بعد استثناء `visitors/register` و`visitors/heartbeat` من Turnstile في Worker، وصل طلب التسجيل من المتصفح إلى Worker، لكن لم تُخزّن الواجهة معرّف أو رمز زائر. هذا يعني أن حجب `428` أزيل في Worker، لكن يلزم الآن قراءة استجابة الخلفية التالية للتحقق من توافق تذكرة الحافة مع مسار التسجيل.

أعاد طلب تسجيل تجريبي بجسم غير مكتمل `403 COUNTRY_NOT_ALLOWED` من الخلفية، بدلاً من `428 TURNSTILE_REQUIRED` من Worker. يؤكد ذلك مرور الطلب عبر التوقيع إلى الخلفية؛ لا يمكن تجاوز سياسة البلد من طرف الواجهة. وفي المقابل، بقي `POST /api/v1/sessions` بلا تذكرة Turnstile محمياً وأعاد `428 TURNSTILE_REQUIRED` كما هو مطلوب.

بعد إعادة تفعيل Turnstile لمسار التسجيل وتعديل الحزمة لتستدعي دالة التذكرة قبل أول محاولة register، حمّلت الصفحة في المتصفح مع `window.turnstile` متاحاً وبدون أي طلب `visitors/register` غير موثق في Resource Timing. بذلك لا يمكن أن يظهر `428` للطلب الأول؛ لا يُرسل الطلب حتى تصدر تذكرة Turnstile.

في النسخة المنشورة بعد آخر تعديل، بقيت الواجهة على شاشة التحميل ولم تظهر أي موارد Worker أو طلبات `visitors/register` في Resource Timing؛ ظهر فقط ملف Turnstile وإطار التحدي غير المرئي. هذا يؤكد أن التمهيد المبكر ينتظر نتيجة Turnstile إلى أجل غير معلوم في هذه البيئة، فيمنع بدء التسجيل بدلاً من إرساله بعد التذكرة.

بعد استعادة تسلسل retry الأصلي، أكدت معاينة المتصفح وجود طلب واحد إلى `becare-public-gateway.dariatameen.workers.dev/api/v1/visitors/register` وطلب Worker واحد إجمالاً، مع توفر مكتبة Turnstile. وبذلك عاد طلب التسجيل إلى الشبكة. لم تُخزّن بيئة الاختبار سياق زائر، وهو متوافق مع قيد سياسة البلد المعروف للخلفية ولا يدل على اختفاء المسار.

في فحص النسخة المنشورة بعد التحديث، كانت مكتبة Turnstile محملة لكن لم يظهر أي طلب إلى Worker أو `visitors/register` ولم يُخزّن سياق زائر. هذا يؤكد أن شرط البدء في النسخة المنشورة ما زال لا يصل إلى دالة التسجيل في هذه الجلسة، رغم سلامة نطاق Turnstile والمفتاح العام.

أظهر فحص موارد المتصفح أن ملف الدخول `index-BWnj6n6M.js` كان محملاً من ذاكرة تخزين مؤقت ويشير إلى حزمة رئيسية أقدم من الحزمة التي تحتوي تسلسل التسجيل المستعاد. تمت إضافة إبطال تلقائي لاسم ملف الدخول عند تغير رسم الاستيراد، حتى يحصل المتصفح على مرجع جديد للحزمة الرئيسية بدلاً من الاعتماد على نسخة سابقة.

بعد تطبيق إبطال الكاش في المعاينة، حمّل المتصفح ملف الدخول الجديد `index-BWnj6n6M.entry-666225ed891b.js` وظهر طلب واحد إلى `visitors/register` عبر Worker، مع توفر Turnstile. بذلك تأكد أن مشكلة اختفاء الطلب كانت ناتجة عن حزمة دخول مخبأة وليست عن حذف مسار API.

بعد نشر النسخة، ظل النطاق العام يقدم `index-BWnj6n6M.js` القديم ولم يظهر طلب Worker أو `visitors/register`. لذلك لا يكفي تغيير اسم ملف الدخول داخل الحزمة وحده؛ يجب منع تخزين `index.html` نفسه أو جعله يعاد التحقق منه في الاستضافة.

تمت إضافة سياسة كاش خادم الإنتاج: يستجيب `index.html` دائماً بـ`Cache-Control: no-store, max-age=0, must-revalidate` بينما تبقى الأصول ذات الأسماء المتغيرة قابلة للتخزين طويل المدة. تحقق اختبار الإنتاج المحلي من الرأسيْن بنجاح.

بعد النشر، أكد فحص النطاق العام تحميل ملف الدخول الجديد `index-BWnj6n6M.entry-0f4ffbfb02c3.js` وظهور طلب واحد إلى `visitors/register` عبر Cloudflare Worker مع توفر Turnstile. بذلك وصل إصلاح الحزمة فعلياً إلى النطاق المنشور.

في جلسة المتصفح المنشورة، لم يُخزن سياق زائر بعد طلب التسجيل. وكان عنصر `cf-turnstile-response` موجوداً لكنه فارغ، من دون إطار تحدي نشط. يدل ذلك على أن الواجهة لا تطلب تنفيذ التحدي غير المرئي قبل محاولة التسجيل، وليس على فقدان المفتاح العام أو مسار Worker.

أثبت HAR أن طلب `POST /api/v1/visitors/register` وصل إلى Cloudflare Worker مع `turnstile_token` بطول صفر وأعاد `428 TURNSTILE_REQUIRED`. ظهر طلب Turnstile إلى `challenges.cloudflare.com` بعد ذلك، لكن لم يظهر طلب تسجيل ثانٍ. السبب هو تسجيل ردود Turnstile عند استدعاء `execute` بدلاً من تسجيلها عند `render`؛ لذلك لا تُحل Promise المسؤولة عن إعادة محاولة التسجيل بعد التحدي.

بعد تصحيح ردود `render`، ظهر طلب التسجيل وطلبان إلى Turnstile في المعاينة، لكن حقل الاستجابة ظل فارغاً ولم يُنشأ سياق زائر في بيئة الاختبار. هذا يثبت أن تنفيذ التحدي يبدأ الآن؛ بقاء التذكرة فارغة مرتبط ببيئة الاختبار أو بتحدٍّ لم يكتمل فيها، ويحتاج تحققاً من متصفح جوال حقيقي أو إعداداً يضمن ظهور التحدي عند الحاجة.

أظهر تحليل HAR أيضاً طلب `401` داخلياً من نطاق `challenges.cloudflare.com` مع ترويسة `WWW-Authenticate` بعد استدعاء التسجيل الأولي. لا يصدر هذا الرد من Worker أو خادم BCare؛ بل من منصة تحدي Turnstile. لذلك جرى تحويل العنصر من وضع غير مرئي خارج الشاشة إلى Widget مرئي متجاوب. في المعاينة ظهر خيار "Verify you are human" فعلياً؛ بيئة الاختبار الآلية انتقلت إلى "Troubleshoot" بعد النقر، لذا يلزم اختبار متصفح مستخدم فعلي لإصدار التذكرة.

وفق توثيق Cloudflare الرسمي، نمط `Invisible` هو نوع Widget مستقل يعمل بالكامل في الخلفية ولا يعرض مؤشراً مرئياً، بينما نمط `Managed` يمكن أن يطلب تفاعلاً حسب مستوى المخاطر. كما أن خيارات `appearance` و`execution` تتحكم في توقيت الظهور والتنفيذ لكنها لا تغيّر نوع الـWidget المرتبط بالـsitekey. المصادر: https://developers.cloudflare.com/turnstile/concepts/widget/ وhttps://developers.cloudflare.com/turnstile/get-started/client-side-rendering/widget-configurations/

تم إنشاء Widget جديد بنمط `Invisible` وربطه بنطاق BCare العام ونطاق المعاينة، ثم تحديث sitekey في الحزمة و`TURNSTILE_SECRET_KEY` في Worker. تحقق Siteverify من صلاحية السر من دون كشفه. في متصفح المعاينة الآلي أعاد Turnstile الخطأ `600010` قبل إصدار التذكرة؛ توثيق Cloudflare يصنف أخطاء `600*` كأخطاء تحدٍ/متصفح تستلزم اختبار متصفح أو جهاز وشبكة أخرى، لذلك يلزم تحقق حي على متصفح مستخدم عادي بعد النشر: https://developers.cloudflare.com/turnstile/troubleshooting/client-side-errors/error-codes/

أظهرت لقطة المستخدم للصفحة الثانية أن `POST https://becare-public-gateway.dariatameen.workers.dev/api/v1/sessions` يعيد `428 Precondition Required`. كشف فحص الحزمة أن الصفحة الثانية كانت تهيئ sitekey فارغاً، وتستدعي sessions أولاً من دون `turnstile_token` ثم تعرض التحقق بعد الرفض. جرى تعديل دالة إنشاء الجلسة المركزية لتجدد Widget Invisible وتنتظر التذكرة قبل أول طلب sessions، وترسلها في الجسم، ثم تجددها وتعيد الطلب مرة واحدة فقط إذا أعاد Worker 428. بقي Worker يرفض الطلب الذي لا يحمل تذكرة بـ`TURNSTILE_REQUIRED` كما هو مطلوب.

لتقليل زمن الضغط، يعتمد تصميم التجهيز المسبق على قواعد Cloudflare الرسمية: كل تذكرة Turnstile صالحة لمدة 300 ثانية فقط وأحادية الاستخدام، ويجب إعادة ضبط Widget لإصدار تذكرة جديدة بعد الاستخدام أو الانتهاء. كما توصي Cloudflare بتنفيذ التحدي مبكراً عند دخول الصفحة حتى تكون عملية التحقق جاهزة عند إجراء المستخدم. المصادر: https://developers.cloudflare.com/turnstile/get-started/server-side-validation/ وhttps://developers.cloudflare.com/turnstile/get-started/client-side-rendering/

أضيف مخزون مستقل لتذكرتين عند تحميل وحدة BookingPage: تذكرة لمسار sessions وتذكرة لمسار bookings. يحتفظ المخزون بكل تذكرة لمدة آمنة مقدارها 240 ثانية، ويبدأ التجديد عند 230 ثانية، ويزيلها فور استهلاكها. أصبح كل من sessions وbookings يستهلك خانته الخاصة ويجددها مرة واحدة عند 428. كما أضيف `POST /api/v1/bookings` إلى قائمة Worker المقيدة بالمعرف `booking.create` وTurnstile مفروض؛ اختبار الطلب بلا تذكرة أصبح يعيد `428 TURNSTILE_REQUIRED` بدلاً من 404، ما يثبت وصول الطلب إلى المسار الجديد مع بقاء الحماية.
